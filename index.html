A hands-on introduction

What is Jev?

Most of what a workflow does is mechanical: run this step, wait for that one, check whether the tests passed. Every so often it reaches a question that needs judgement, like whether a change touches security or whether a reply in Slack means yes. This page is for anyone building those workflows, whether in n8n, a CI pipeline or your own agent runner. It explains Jev, a model that answers those questions with a number you can act on, and walks through using it to decide which way a workflow goes.

The API examples come from TypeSafe's docs. The gate is a small sketch that lives in the repo and runs.

What kind of model this is

Think about how you'd usually get a yes or no out of a language model. You write a prompt that ends with "answer PASS or FAIL", the model writes a sentence, and your code searches that sentence for the word PASS. It works most of the time. Then one day the model writes "this should NOT PASS", and your code ships it anyway.

Jev, from TypeSafe, removes that whole step. You don't prompt it and it never writes anything. You send it the thing you want judged plus a list of typed questions about it, and it sends back an answer to each question with a probability attached. TypeSafe calls this a System One model, borrowing the psychology term for fast, automatic judgement, as opposed to the slow, step-by-step reasoning a chat model does.

What you give up is flexibility. Jev only picks among options you provide. It can't explain an answer, call a tool, or work through a problem in steps. In exchange it's fast (tens to a few hundred milliseconds), cheap (the 1,326 calls behind the workflow-gate examples cost seven cents in total, by OpenRouter's billing), and its probabilities mean something. TypeSafe trains it to be calibrated: across many calls, the answers it gives 0.9 should be right about nine times out of ten.

The kinds of question

For text, there are three, and most of the craft is picking the right one. A noul is a yes/no question, and its answer is simply the probability of yes. Reach for it whenever you'd naturally say "is it true that…". A choice picks one option from a list of up to 255 and gives a probability for each, all adding up to 1. Use it when exactly one option can be right. A score places the state on an ordered scale you describe, like calm, frustrated, furious, and tells you where it falls as a decimal, along with a probability for each step. (There's also a fourth kind, box, which finds where something is in an image. It doesn't come up in workflow gates, so it's left out here.)

TypeIt asksYou get back
noulIs this statement true?noul, the probability of yes, from 0 to 1
choiceWhich of these options?choice, probabilities for every option, confidence
scoreWhere on this scale?score as a decimal, probabilities for every step, legend, confidence

A request has three parts. The state is whatever you want judged. It can be a string or any JSON, and JSON with clear field names tends to get better answers than a wall of text. The questions are a map you write, from ids you pick to typed questions. The answers come back under those same ids. Jev evaluates every question separately and in parallel against the same state, so asking ten questions takes about as long as asking one.

The department answer is as clear as it gets: all the probability on technical, so confidence is 1.0. Frustration is more interesting. The score of 0.67 sits between "calm" and "frustrated but civil" because Jev split its belief two to one between them, and the confidence of 0.5 says it's torn.

Confidence isn't the same as the winning probability. For a choice, TypeSafe rescales the top probability so that an even split counts as 0 and certainty as 1. That makes it comparable across questions with different numbers of options: 0.5 is a weak answer when there are two options and a strong one when there are ten. Try it:

A score's confidence also looks at where the leftover probability sits. Being torn between two neighbouring steps costs less than being torn between opposite ends: with three steps, a 50/50 split between the top two gives 0.25, while a 50/50 split between the bottom and the top gives 0. Making a call

There's a single endpoint. You can call TypeSafe directly, or go through OpenRouter, which takes the same request body with a different URL and model name:

# TypeSafe (get a key at console.typesafe.ai/settings/keys)
curl -s https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"jev-latest","state":"…","questions":{…}}'

# OpenRouter
curl -s https://openrouter.ai/api/v1/systemone \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"~typesafe/jev-latest", …}'

If you like working in a shell, stefafafan/jev is a small CLI that reads the state from stdin and prints JSON. It deliberately leaves the threshold to you, so the actual decision stays visible in your own script:

git diff main | jev noul "Could this change introduce a regression?" \
  | jq -e '.answers.result.noul < 0.2' && echo ship

From Python there's an official SDK (uv add typesafe-sdk). Inside a workflow runner, though, a plain urllib POST is enough and saves a dependency.

Writing good questions

Keep each question small

The best questions are ones a knowledgeable person could answer in a few seconds without looking anything up. "Is this PR good?" isn't one of those. It's really three or four smaller questions bundled together: does it touch auth, does it have tests, is it only docs. Ask those separately and combine the answers in code. Later, when you decide tests matter more than they used to, you change a number in an if instead of rewording a prompt and hoping.

Ask the questions you might need

Each question is judged on its own, so an extra question doesn't muddy the others, and it barely adds time. That means it's fine to ask things you'll only need on some branches. If a later step cares about a ticket's language only when it's a billing ticket, ask about the language anyway and ignore the answer when it doesn't matter. TypeSafe calls this speculative fan-out.

Give "I don't know" somewhere to go

A probability beats a plain yes or no because it can tell you when the model isn't sure. To use that, split the range into three bands: act on a confident yes, skip on a confident no, and send everything in between to a person. How wide to make the middle depends on what a mistake costs. A narrow band is fine for routing a ticket. For anything that merges code touching auth, you want a wide one. Drag the slider to get a feel for it:

Leave exact checks to code

Jev is for judgements that need reading comprehension. Anything you can check exactly, like comparing dates, doing arithmetic, or testing whether a field equals PASS, belongs in ordinary code. Code gets those right every time, and asking Jev would only add a chance of being wrong.

How a gate decides

A gate is a fork in a workflow. It has a short list of paths, each with a condition, and the run takes the first path whose condition holds. Most conditions are plain rules: every step passed, some step failed, or "always" as the fallback at the end. Good workflow tools also let you write a condition in plain English, like "the change touches security", and that's the kind Jev is for.

Three things in those two lines are worth noticing.

  • It's slow. Each condition starts a whole agent run, and the paths are checked one after another, so a gate with three plain-English paths can mean three agent runs just to pick a direction.
  • It can misread the answer. It looks for the letters PASS, so "this should NOT PASS" counts as a pass.
  • It can't say "not sure". Every condition comes out yes or no, even when the agent was clearly torn.

Jev helps with all three. One call answers every plain-English condition at once, the answer is a number rather than a sentence, and the number tells you how sure Jev is. Pick a change and walk through the gate one path at a time:

    Building a Jev gate

    A yes/no question for each path

    The natural first idea is one multiple-choice question: "which way should this go?" It's worth seeing why that doesn't fit. A choice assumes exactly one option is right, so its probabilities always add up to 1. A gate's conditions don't work like that. More than one can be true at once, since a change can touch auth and also have no tests, and the gate's order already decides which one wins. Asked as a choice, Jev has to split its belief between them, and both come out looking uncertain even though both are clearly true.

    Two things that are both true
    One multiple-choice question
    A yes/no question for each

    Real Jev answers on real pull requests, asked both ways. Of the pull requests where both yes/no answers came back at 0.8 or above, the multiple-choice question put one of the two below 0.8 in .

    Asking a separate yes/no question for each condition avoids that. You still send all of them in one request, and the gate's order decides which true condition wins.

    A choice is the right tool when the options really do exclude each other, like routing a ticket to frontend, backend or infra. There, exactly one answer is correct and order doesn't matter.

    The line to look at closely is p >= NO. Imagine Jev is unsure about the second path and the loop simply moved on. The third path, or the "always" fallback, would win by default, and the gate would have treated "unsure" as "no" without anyone deciding that. So when Jev is unsure, the gate stops and takes the path marked "not sure", which you'd point at a person. If there isn't one, the gate stops with nothing chosen, the same as when no condition matches.

    The state you send is just what the gate knows, as JSON: each earlier step's verdict and summary, plus whatever triggered the run, capped so a huge webhook body doesn't go out whole.

    Plugging it in

    Jev is a separate service with its own API key, and a gate would send it step summaries and raw webhook payloads. That's a good reason to make it opt-in. The cleanest shape is a small hook in your workflow runner: before checking a gate the usual way, it asks any installed plugin whether it wants to decide. A Jev plugin answers, and everyone without one gets the old behaviour.

    If your tool has no plugin system, the same idea works as one step that calls choose_path before the fork. Whichever way you wire it, save the why string with each run, so the log can say security · jev 0.93 and you can see why a run went the way it did.

    Other places it would help

    Gates are the obvious spot, but anywhere a workflow asks an agent for a quick judgement call and then reads its prose, Jev could answer instead:

    WhereThe questionType
    An approval from chatIs this reply an approval, a rejection, or a question back?choice
    A webhook triggerIs this payload worth starting a run for? Filtering here saves an agent run on noise.noul
    An agent's own verdictHow well does its summary meet the goal? A better signal than the agent saying PASS.score
    The end of a chat sessionDid it end in failure or frustration?noul

    Things to watch out for

    • Your data leaves the machine. Step summaries and trigger payloads go to TypeSafe or OpenRouter, so cap them, redact them, and tell people in the plugin's description.
    • Decide in advance what happens when a call fails. A gate should fall back to the usual check or go to "not sure". It should never fall through to "always", because a timeout that quietly takes the default path is about the worst way a gate can fail.
    • Calibration describes many calls, not one. A 0.9 means Jev is right about nine times in ten across lots of similar answers. It doesn't mean this particular answer is certain. Log each answer next to the path the gate took, and tune YES and NO from what you see.
    • Phrase questions as claims. "The change weakens an auth or CSRF control" gets better answers than "Is it risky?". When "yes" needs a definition, a noul accepts criteria with a description for true and for false.
    • A noul has no confidence field, because a value near 0.5 already says Jev is unsure. Only choice and score answers carry a separate confidence.
    • Set a timeout of a few seconds, with a fallback, so a slow API can't stall a run.

    Where to go from here

    1. Take one of your own plain-English conditions and send it through the curl above, with a real step summary as the state. Seeing the numbers on your own data is the quickest way to build intuition.
    2. Run python3 test_judge.py, then change YES and NO and watch which cases flip.
    3. Decide what to build first. A better default check helps everyone, with or without Jev. The hook and a Jev plugin are what let Jev do the deciding.
    4. See how it holds up on real data. Workflow gates runs these ideas on a busy open-source repo's issues and pull requests, and n8n & design systems tries them on an n8n template and a UI kit.
