Jev, for workflow gates

Jev is a model you can't chat with. You give it state and typed questions, and it returns probabilities your code can branch on. That makes it a good fit for the Judgement arm in your workflow gates.

Grounded in workflow/runner.py from the Workflows PR (#94367) and the TypeSafe docs. The runnable code is in this folder.

What Jev is

Jev is TypeSafe's first System One model, released September 2026. A chat model writes text and you parse it. Jev skips the text: every answer comes back already typed.

An LLM is a writer you coax into acting like a function. Jev starts out as a function.

Each request has three parts:

  • state: the thing being judged. A string, or any JSON. Structure helps.
  • questions: a map from ids you choose to typed questions. All of them run in parallel against the same state, in one call. Adding questions barely changes latency.
  • answers: the same ids, each holding a typed value and a probability. No prose and no parser.

The trade is that Jev can only pick from options you list. It can't invent one, explain itself, call tools, or reason step by step. In return a call takes tens to hundreds of milliseconds and costs fractions of a cent. Its probabilities are trained to be calibrated: across many calls, answers it gives 0.9 should be right about 90% of the time.

Call it

The API is a single endpoint, served by TypeSafe directly or through OpenRouter:

# TypeSafe: key from console.typesafe.ai/settings/keys
curl -s https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"jev-latest","state":"…","questions":{…}}'

# OpenRouter: same body, different URL and model id
curl -s https://openrouter.ai/api/v1/systemone \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"~typesafe/jev-latest", …}'

For the shell, stefafafan/jev is the most Unix-like CLI: state comes in on stdin, JSON goes out, and thresholds stay in jq, where you can see them.

git diff main | jev noul "Could this change introduce a regression?" \
  | jq -e '.answers.result.noul < 0.2' && echo ship

From Python there's uv add typesafe-sdk. Inside Hermes, use plain urllib instead: the runner has no business taking a dependency for one POST. The catalog's jev-judge plugin made the same call and is stdlib-only.

Thinking in Jev

Ask atomic questions, then combine them in code

Each question should be a gut check that a knowledgeable person could answer in a few seconds. "Is this PR good?" is several questions bundled together. Split it into "touches auth?", "has tests?" and "is it only docs?", then combine the answers with an if. When your priorities change, you edit a coefficient, not a prompt.

Ask more than you need

Questions run in parallel and each is judged in isolation, so speculative ones are nearly free and can't pollute each other's context. Ask everything a branch might need and ignore the answers you don't use. TypeSafe calls this speculative fan-out.

Treat "I'm not sure" as a third answer

Split the probability into three bands. Act when Jev is confident, refuse when it's confident the other way, and hand the middle to a person. How wide you make the middle band should depend on how costly a wrong answer is. Drag the slider:

Know what it can't do

Arithmetic, date comparisons, "is verdict equal to PASS": keep all of that in code. Jev is for semantic judgement, the part a regex can't do.

Your gates today

A gate has ordered arms, and the first one that matches wins. Four modes are deterministic (all-pass, any-fail, checks, always). The fifth, labelled Judgement in the inspector, is prose, and it does this:

That has three problems, and Jev fixes each one:

  • Slow: every Judgement arm runs a full agent step with up to 8 iterations, one arm after another. Jev answers all of a gate's arms in one call, usually under a second.
  • Fragile: when the step returns no explicit verdict, the arm is decided by a substring match, so a reply of "this should NOT PASS" takes the arm. Jev returns a number, so there's nothing to misread.
  • Overconfident: the answer is yes or no, with no way to say "not sure". Jev's probability gives the gate that middle option.

A Jev gate

Use a Noul per arm, not a Choice across arms

A Choice across the arms looks like the obvious fit, and it's the wrong one here. A Choice's probabilities sum to 1, which assumes exactly one option is true. Your arms don't work that way: they're ordered, and "touches auth" and "touches tests" can both be true. A Choice would split the probability between them and both arms would look unsure. So ask one Noul per Judgement arm, all in one request, and let the gate's existing order decide among them.

Use a Choice when the options really are mutually exclusive, for example "route to frontend, backend or infra". Order doesn't matter there and one answer is correct.

The line that matters most is the p >= NO branch. If Jev is unsure about arm 2 and the loop just moved on, arm 3 or the always fallback would win by default. The gate would have quietly answered no. Instead it stops and routes to an unsure arm, which you wire to the Human approval step the graph already has. If no unsure arm exists, the gate fails with the error it already raises when no arm matches.

Wiring it in

Jev is a third-party service with its own key, and the gate sends it step summaries and raw webhook payloads. That's a reason to keep it out of core: the runner gets a seam, and Jev is one plugin that uses it. This is a sketch; none of it is on your branch yet.

Three small changes on the canvas side make this visible:

  • An "unsure" predicate mode in scenario.ts's PREDICATE_MODES, labelled something like Not sure, with the hint "Jev couldn't call it, so wire this to a Human approval". holds() already returns False for unknown modes, so the existing rule logic needs no change.
  • The why in the gate's summary. Pass it into GateEvaluated so the feed reads security · jev 0.93 instead of review FAIL → …. Then you can see why a run took the branch it did.
  • A better default for people without Jev. Replace the 8-iteration agent with one structured call to the auxiliary model that returns a typed verdict. That fixes the "NOT PASS" bug for everyone.

Other seams

Anywhere in workflows where software has to make a semantic call that an agent currently makes in prose:

WhereQuestionType
Approval from a chatIs this reply approve, reject, or a question back?choice
Webhook triggerIs this payload worth starting a run for? Filters noise before it costs an agent turn.noul
Agent step verdictScore the summary against the step's goal instead of trusting a self-reported PASS.score
Hermes events"A session ended": did it end in failure or frustration?noul

Prior art: Hermes's plugin-catalog/ already lists jev-judge (a pre_tool_call gate in shadow mode), jev-approvals, jev-agent-router and others. Read jev-judge first; it handles redaction, payload caps, fail-open and the JSONL decision log.

Sharp edges

  • Data leaves the machine. Summaries and trigger payloads go to TypeSafe or OpenRouter. Cap them, redact them, and say so in the plugin description, as jev-judge does.
  • Decide how it fails. For a gate, a failed call should fall back to the built-in judge or route to the unsure arm. It must never fall through to always, because a timeout that silently takes the default branch is the worst bug a gate can have.
  • Calibration holds in aggregate. 0.9 means "right about 9 times in 10 across many calls", not "certain this time". Log every noul next to the arm the gate took, then tune YES/NO from real runs.
  • Write instructions as claims. "The change weakens an auth or CSRF control" works better than "Is it risky?". For a Noul you can add criteria: {true, false} when "yes" needs a definition.
  • Noul has no confidence field. A value near 0.5 is the uncertainty. Choice and Score carry a separate confidence.
  • Set a timeout. A five-second cap with a fallback keeps a stalled API from wedging a run's loop thread.
