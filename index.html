Tutorial

Using Jev for workflow gates

Most of what a workflow does is mechanical: run this step, wait for that one, check whether the tests passed. Every so often it reaches a question that needs judgement, like whether a change touches security or whether a reply in Slack means yes. This tutorial is about handing those questions to Jev, a model that answers them with a number you can act on.

The gate examples come from the Judgement arm in the Workflows PR (#94367), and the API examples from TypeSafe's docs. All the code lives in the repo and runs.

What kind of model this is

Think about how you'd usually get a yes or no out of a language model. You write a prompt that ends with "answer PASS or FAIL", the model writes a sentence, and your code searches that sentence for the word PASS. It works most of the time. Then one day the model writes "this should NOT PASS", and your code ships it anyway.

Jev, from TypeSafe, removes that whole step. You don't prompt it and it never writes anything. You send it the thing you want judged plus a list of typed questions about it, and it sends back an answer to each question with a probability attached. TypeSafe calls this a System One model, borrowing the psychology term for fast, automatic judgement, as opposed to the slow, step-by-step reasoning a chat model does.

A request has three parts. The state is whatever you want judged. It can be a string or any JSON, and JSON with clear field names tends to get better answers than a wall of text. The questions are a map you write, from ids you pick to typed questions. The answers come back under those same ids. Jev evaluates every question separately and in parallel against the same state, so asking ten questions takes about as long as asking one.

What you give up is flexibility. Jev only picks among options you provide. It can't explain an answer, call a tool, or work through a problem in steps. In exchange it's fast (tens to a few hundred milliseconds), cheap (the 926 calls behind the workflow-gate examples cost under five cents in total), and its probabilities mean something. TypeSafe trains it to be calibrated: across many calls, the answers it gives 0.9 should be right about nine times out of ten.

The three kinds of question

There are only three, and most of the craft is picking the right one. A noul is a yes/no question, and its answer is simply the probability of yes. Reach for it whenever you'd naturally say "is it true that…". A choice picks one option from a list of up to 255 and gives a probability for each, all adding up to 1. Use it when exactly one option can be right. A score places the state on an ordered scale you describe, like calm, frustrated, furious, and returns where it falls as a decimal.

Making a call

There's a single endpoint. You can call TypeSafe directly, or go through OpenRouter, which takes the same request body with a different URL and model name:

# TypeSafe (get a key at console.typesafe.ai/settings/keys)
curl -s https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"jev-latest","state":"…","questions":{…}}'

# OpenRouter
curl -s https://openrouter.ai/api/v1/systemone \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"~typesafe/jev-latest", …}'

If you like working in a shell, stefafafan/jev is a small CLI that reads the state from stdin and prints JSON. It deliberately leaves the threshold to you, so the actual decision stays visible in your own script:

git diff main | jev noul "Could this change introduce a regression?" \
  | jq -e '.answers.result.noul < 0.2' && echo ship

From Python there's an official SDK (uv add typesafe-sdk). For something like the Hermes runner, though, a plain urllib POST is enough and saves a dependency. The jev-judge plugin in Hermes' catalog does exactly that.

Writing good questions

Keep each question small

The best questions are ones a knowledgeable person could answer in a few seconds without looking anything up. "Is this PR good?" isn't one of those. It's really three or four smaller questions bundled together: does it touch auth, does it have tests, is it only docs. Ask those separately and combine the answers in code. Later, when you decide tests matter more than they used to, you change a number in an if instead of rewording a prompt and hoping.

Ask the questions you might need

Each question is judged on its own, so an extra question doesn't muddy the others, and it barely adds time. That means it's fine to ask things you'll only need on some branches. If a later step cares about a ticket's language only when it's a billing ticket, ask about the language anyway and ignore the answer when it doesn't matter. TypeSafe calls this speculative fan-out.

Give "I don't know" somewhere to go

A probability beats a plain yes or no because it can tell you when the model isn't sure. To use that, split the range into three bands: act on a confident yes, skip on a confident no, and send everything in between to a person. How wide to make the middle depends on what a mistake costs. A narrow band is fine for routing a ticket. For anything that merges code touching auth, you want a wide one. Drag the slider to get a feel for it:

Leave exact checks to code

Jev is for judgements that need reading comprehension. Anything you can check exactly, like comparing dates, doing arithmetic, or testing whether a field equals PASS, belongs in ordinary code. Code gets those right every time, and asking Jev would only add a chance of being wrong.

How gates decide today

In the Workflows plugin, a gate has a list of arms, and the run takes the first arm whose condition holds. Four kinds of condition are plain rules: every input passed, any input failed, a set of checks on named steps, and "always" as the fallback at the end. The fifth kind is labelled Judgement in the inspector (prose in the code), and it lets you write the condition in plain English. Here's how the runner evaluates it:

Three things in that code are worth noticing.

  • It's slow. Each Judgement arm starts a full agent step, allowed up to eight iterations, and the arms are checked one after another. A gate with three Judgement arms can mean three agent runs just to choose a branch.
  • It can misread the answer. When the step doesn't return an explicit verdict, the runner looks for the letters PASS in the summary, so "this should NOT PASS" counts as a pass.
  • It can't say "not sure". Every arm comes out yes or no, even when the agent was clearly torn.

Jev helps with all three. One call answers every Judgement arm at once, the answer is a number rather than a sentence, and the number tells you how sure Jev is.

    Building a Jev gate

    One yes/no question per arm

    The natural first idea is a single choice question: "which of these arms should the run take?" It's worth seeing why that doesn't fit. A choice assumes exactly one option is right, so its probabilities always add up to 1. Gate arms don't work like that. They're checked in order, and more than one can be true at once, since a change can touch auth and also have no tests. Asked as a choice, Jev has to split its belief between those two arms, and both come out looking uncertain even though both are clearly true.

    Asking a separate noul for each arm avoids that. You still send all of them in one request, and the gate's existing order decides which of the true arms wins.

    Choice is the right tool when the options really do exclude each other, like routing a ticket to frontend, backend or infra. There exactly one answer is correct, and order doesn't matter.

    The branch to look at closely is p >= NO. Imagine Jev is unsure about the second arm and the loop simply moved on. The third arm, or the always fallback, would win by default, and the gate would have treated "unsure" as "no" without anyone deciding that. So when Jev is unsure, the gate stops and takes the arm marked unsure, which you'd wire to a Human approval step. If the gate has no such arm, it fails the same way it already does when nothing matches.

    The state you send is just the gate's inputs as JSON: each upstream step's verdict and summary, plus the trigger payload, capped so a huge webhook body doesn't go out whole.

    Fitting it into Hermes

    Jev is a separate service with its own API key, and a gate would send it step summaries and raw webhook payloads. That's a good reason to keep it out of Hermes itself. A cleaner shape is a small hook in the runner that lets any plugin make the gate decision, with Jev as one plugin that uses it. Nothing below exists yet. It's a sketch of how the pieces could fit together.

    On the canvas, three small changes would make this usable:

    • A new kind of arm, something like Not sure, added to PREDICATE_MODES in scenario.ts, with a hint telling people to wire it to a Human approval step. holds() already returns False for modes it doesn't recognise, so the rule logic doesn't need to change.
    • The gate's reasoning in the run feed. If the why string goes into the GateEvaluated event, the feed can show security · jev 0.93, and you can see at a glance why a run went the way it did.
    • A better fallback for people without a Jev key: swap the eight-iteration agent for one structured call to the auxiliary model that returns a typed verdict. That change alone fixes the "NOT PASS" bug.

    Other places it would help

    Gates are the obvious spot, but anywhere a workflow asks an agent for a quick judgement call and then reads its prose, Jev could answer instead:

    WhereThe questionType
    An approval from chatIs this reply an approval, a rejection, or a question back?choice
    A webhook triggerIs this payload worth starting a run for? Filtering here saves an agent turn on noise.noul
    An agent step's verdictHow well does the summary meet the step's goal? A better signal than the step's own PASS.score

    Hermes' plugin catalog already has several Jev plugins, including jev-judge (a pre_tool_call gate that starts in shadow mode), jev-approvals and jev-agent-router. jev-judge is worth reading before you write your own, since it already handles redaction, payload caps, failing open and a log of every decision.

    Things to watch out for

    • Your data leaves the machine. Step summaries and trigger payloads go to TypeSafe or OpenRouter, so cap them, redact them, and say so in the plugin's description the way jev-judge does.
    • Decide in advance what happens when a call fails. A gate should fall back to the built-in judge or route to the unsure arm. It should never fall through to always, because a timeout that quietly takes the default branch is about the worst way a gate can fail.
    • Calibration describes many calls, not one. A 0.9 means Jev is right about nine times in ten across lots of similar answers. It doesn't mean this particular answer is certain. Log each noul next to the arm the gate took, and tune YES and NO from what you see.
    • Phrase questions as claims. "The change weakens an auth or CSRF control" gets better answers than "Is it risky?". When "yes" needs a definition, a noul accepts criteria with a description for true and for false.
    • A noul has no confidence field, because a value near 0.5 already says Jev is unsure. Only choice and score answers carry a separate confidence.
    • Set a timeout of a few seconds, with a fallback, so a slow API can't stall a run.

    Where to go from here

    1. Take one of your real gates' Judgement conditions and send it through the curl above, with an actual step summary as the state. Seeing the numbers on your own data is the quickest way to build intuition.
    2. Run python3 test_judge.py, then change YES and NO and watch which cases flip.
    3. Decide what to build first. Replacing the default judge with one structured call helps everyone, with or without Jev. The runner hook and a jev-gate plugin are what let Jev do the deciding.
    4. See how it holds up on real data. Workflow gates runs these ideas against hermes-agent issues and PRs, and n8n & design systems tries them on an n8n template and a UI kit.
