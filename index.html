A hands-on introduction

What is Jev?

Most of what a workflow does is mechanical. Every so often it hits a question that needs judgement: does this change touch security, does this Slack reply mean yes? This page is for anyone building workflows, in n8n, CI or their own agent runner. It explains Jev, a model that answers those questions with a number, and how to use it to pick which way a workflow goes.

API examples are from TypeSafe's docs. The gate code is in the repo and runs.

What kind of model this is

The usual way to get a yes or no from a language model is to end the prompt with "answer PASS or FAIL" and search the reply for PASS. It works until the model writes "this should NOT PASS" and your code ships it.

Jev, from TypeSafe, skips the text. You send it the thing to judge and a few typed questions, and it returns an answer to each with a probability. TypeSafe calls it a System One model: fast, automatic judgement rather than step-by-step reasoning.

The trade is flexibility. Jev only picks from options you give it, and it can't explain itself, call tools or reason in steps. In return it's fast (tens to hundreds of milliseconds), cheap (the 1,326 calls behind the examples cost seven cents) and calibrated: answers it gives 0.9 are right about nine times in ten.

The kinds of question

For text there are three. A noul is yes/no, and its answer is the probability of yes. A choice picks one of up to 255 options, with a probability for each; use it when exactly one can be right. A score places the state on an ordered scale you describe (calm, frustrated, furious) and returns a decimal plus a probability per step. A fourth kind, box, finds things in images and doesn't come up here.

TypeIt asksYou get back
noulIs this statement true?noul, the probability of yes, from 0 to 1
choiceWhich of these options?choice, probabilities for every option, confidence
scoreWhere on this scale?score as a decimal, probabilities for every step, legend, confidence

Every request has a state, a string or any JSON (clear field names help), and questions keyed by ids you pick. Answers come back under the same ids. Each question is judged separately and in parallel, so ten take about as long as one.

Confidence isn't the winning probability. For a choice, TypeSafe rescales the top probability so an even split is 0 and certainty is 1, which means a confidence of 0.5 says the same thing whether there are two options or ten. Try it:

Making a call

There's one endpoint, from TypeSafe directly or through OpenRouter (same body, different URL and model name):

# TypeSafe (get a key at console.typesafe.ai/settings/keys)
curl -s https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"jev-latest","state":"…","questions":{…}}'

# OpenRouter
curl -s https://openrouter.ai/api/v1/systemone \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"~typesafe/jev-latest", …}'

In a shell, stefafafan/jev reads the state from stdin and prints JSON, leaving the threshold to you:

git diff main | jev noul "Could this change introduce a regression?" \
  | jq -e '.answers.result.noul < 0.2' && echo ship

From Python there's an SDK (uv add typesafe-sdk), though inside a workflow runner a plain urllib POST saves a dependency.

Writing good questions

Keep each question small

Good questions are ones an expert could answer in seconds. "Is this PR good?" is really several: does it touch auth, does it have tests, is it only docs. Ask them separately and combine them in code, so a change in priorities means changing a number, not a prompt.

Ask the questions you might need

Questions are judged independently and barely add time, so ask the ones you'll only need on some branches and ignore the rest. TypeSafe calls this speculative fan-out.

Give "I don't know" somewhere to go

A probability can say when Jev isn't sure. Use three bands: act on a confident yes, skip on a confident no, and send the middle to a person. The costlier a mistake, the wider the middle:

Leave exact checks to code

Anything you can check exactly, like dates, arithmetic or whether a field equals PASS, belongs in code. Jev is for judgements that need reading.

How a gate decides

A gate is a fork: a list of paths, each with a condition, and the run takes the first that holds. Most conditions are rules, like every step passed, some step failed, or "always" as the fallback. Some are plain English, like "the change touches security". Those are Jev's job.

Here's how a plain-English condition usually gets checked:

That has three problems:

  • It's slow: an agent run per condition, one after another.
  • It misreads answers: "this should NOT PASS" contains PASS.
  • It can't say "not sure": every answer is yes or no.

Jev answers every condition in one call, with a number that says how sure it is. Pick a change and step through the gate:

    The obvious approach is one multiple-choice question: "which way should this go?" But a choice assumes exactly one option is right, and a gate's conditions can overlap: a change can touch auth and add no tests. Jev then has to split its belief, and both look uncertain.

    A yes/no question per condition avoids that. Send them all in one request and let the gate's order pick the winner.

    Use a choice when the options truly exclude each other, like routing a ticket to frontend, backend or infra.

    The key line is p >= NO. If an unsure answer just moved on, a later path or the fallback would win by default, quietly treating "unsure" as "no". Instead the gate stops at the "not sure" path, which you point at a person. If there's no such path, it stops with nothing chosen.

    Plugging it in

    Jev is a separate service, and a gate would send it step summaries and webhook payloads, so make it opt-in. The clean shape is a hook in your runner that lets a plugin decide the gate. Without the plugin, nothing changes.

    No plugin system? Call choose_path as a step before the fork. Either way, log the why string so each run says why it went where it did, like security · jev 0.93.

    Other places it would help

    Anywhere else a workflow asks an agent for a quick call and reads its prose:

    WhereThe questionType
    An approval from chatIs this reply an approval, a rejection, or a question back?choice
    A webhook triggerIs this payload worth starting a run for?noul
    An agent's own verdictHow well does the summary meet the goal?score
    The end of a chat sessionDid it end in failure or frustration?noul

    Things to watch out for

    • Data leaves your machine. Cap and redact what you send, and say so.
    • Plan for failure: fall back to the usual check or to "not sure", never to "always".
    • Calibration is about many calls, not one. Log each answer next to what happened and tune YES and NO from that.
    • Phrase questions as claims: "The change weakens an auth or CSRF control" beats "Is it risky?". A noul also accepts criteria that define true and false.
    • Nouls have no confidence; a value near 0.5 is the uncertainty.
    • Set a timeout of a few seconds, with a fallback.
