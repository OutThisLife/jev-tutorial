Jev in n8n and design systems

Most of this work follows a pattern. Something gets made, by an agent or a person, and then a small judgement call decides what happens next: which branch an n8n item takes, which component a frame should use, whether a new button breaks a rule. Jev can make those calls in about 200 ms and tell you how sure it is, so you only pull in a person or a bigger model when it isn't.

Data: n8n's public template library, the Hermes desktop UI kit (components/ui), its DESIGN.md, and its git history · 309 Jev calls, $0.011 · the code and results are in design/

Where it fits

Jev doesn't draw or write code, and it only picks from options you give it. What it's good at is answering small multiple-choice questions about things that already exist, at roughly the cost of writing a log line. So it doesn't replace the model that writes your code. It handles the small decisions before and after:

WhenThe questionType
Before generatingWhich existing component should this frame become?choice over the kit
While generatingWhich variant, token or icon fits this spot?choice
After generatingDoes this break a rule in DESIGN.md?noul per rule
In n8nWhich branch does this item take?choice, feeding a Switch
01 · n8n

Swapping the LLM classifier for one HTTP node

The most common AI pattern in n8n's template library goes trigger, LLM classifier, parse the JSON, Switch. Take "Classify and route DevOps chat requests with Mattermost and Claude". Its classifier is a Sonnet agent with a 5,280-character system prompt, followed by an 85-line Code node that digs the JSON out of code fences, falls back to other when parsing fails, and double-checks that the category is a real one.

For Jev, the template's 7 category descriptions become the options. Here's how both do on 28 new DevOps messages, none of them taken from the template's own examples:

RightMedian timeCost for all 28
The template's Sonnet classifier28 / 282.1 s$0.151
One Jev choice28 / 28180 ms$0.0014

Both got the same answers, but Jev was about 106× cheaper and 12× faster, and it needs no parser. Its response already has the shape the Switch reads. Its three least confident answers were the three messages that really were borderline, which is exactly where an "Ask a human" branch belongs:

  • “how do I get read access to the prod replica?”: question at 0.54
  • “Let's move our secrets from env files to Vault properly, we've never had it”: new_system at 0.66
  • “the release workflow can't push the image, 403 from the registry”: ci_cd_error at 0.89

A workflow you can import

design/n8n/jev-router.json imports straight into n8n. It goes Webhook, Set, an HTTP Request to Jev, Set, then an If on confidence ≥ 0.6 leading to the Switch, with low-confidence items going to "Ask a human". The Jev node takes about 247 ms. For the sample message, about a deploy stuck waiting for a runner, it returns ci_cd_error at 0.95.

// all the "AI" in the workflow is this one HTTP Request node
POST https://openrouter.ai/api/v1/systemone
{ "model": "~typesafe/jev-latest",
  "state": { "message": "{{ $json.message }}" },
  "questions": { "category": { "type": "choice", "criteria": { …the template's categories… } } } }
// Switch on {{ $json.answers.category.choice }}; If on .confidence

n8n's built-in Text Classifier node does the same job with any chat model, but it doesn't give you a confidence. With an unclear item, the best it can do is drop it or send it down an "Other" branch. Jev's probabilities are what make a real "ask a human" branch possible.

02 · Design system · linting

Linting the rules a regex can't check

Hermes' DESIGN.md has rules like "Do not tip menu triggers" and "Do not tip close / dismiss X buttons — the glyph is the label". A regex can't tell what a button is for, but two yes/no questions per <Tip> can: "is this control a close or dismiss button?" and "does it open a menu?". Across all 53 Tips in the desktop app:

TooltipRule it breaksJevWhere
Clearclose / dismiss0.92keybind-settings.tsx
Voice chat engineopens a menu0.92start-voice-button.tsx
New…opens a menu0.94roster-pane-toolbar.tsx
Clear searchclose / dismiss0.95search-field.tsx

All 4 are real violations. "Clear search" lives inside SearchField, so every search box in the app inherits it. A third question, "does hovering teach something new?", gives muddy scores. That depends on what's already visible around the control, which a snippet of code doesn't show. Keep the precise questions in the linter and leave the fuzzy one to a human reviewer.

In a workflow, this check would run after the coding agent and before the PR, with one call per changed Tip. Anything at 0.8 or above becomes a review comment quoting the relevant line of DESIGN.md.

03 · Design system · icons

Does the icon say what the label says?

DESIGN.md asks you to "reuse the existing icon for an action." One noul per icon-only button checks whether the icon clearly communicates its aria-label. Of the app's 36 icon and label pairs, 13 score 0.8 or above, for example trash → Delete, chrome-minimize → Minimize window, close → Close, close → Close, refresh → Refresh. These are the lowest:

IconLabelFitsJev would pickWhere
discardRestore checkpoint0.06refreshuser-message.tsx
kebab-verticalNew branch0.09addcoding-row.tsx
watchManage0.22watchcron-jobs-section.tsx
discardReset to default0.28refreshkeybind-settings.tsx
discardReset HUD size and position0.28screen-normalcontrols.tsx
addStage all0.30check-allindex.tsx

Treat these as things to review, not bugs. The clearest case is "New branch" on a kebab icon: the button opens the branch menu, but the icon says "more". The four discard rows are a naming question. The app consistently uses discard for revert and reset, while Jev expects refresh. Writing that convention into DESIGN.md once would save the next agent from guessing.

04 · Design to code · while generating

Which Button variant goes here?

An agent turning designs into code picks <Button variant="…"> over and over. This test takes 166 Buttons from the app, removes their variant prop, and asks one choice over the 8 variants, described in the words of button.tsx's own comments.

ConfidenceButtonsMatched the code
0.9 or higher3795%
0.6 to 0.93330%
below 0.69621%

Only 39% match overall, mostly because ghost versus text depends on what's around the button, and the snippet doesn't include that. The confident picks are almost always right, though (37 Buttons at 95%). So take Jev's confident picks, and when it's unsure, have the coding agent look at the neighbouring components.

05 · Design to code · before generating

Building on the component that already exists

The most common way a design system drifts is someone hand-building a copy of a component that already exists. The git history has plenty of commits cleaning that up, like "build the task modal on the shared Dialog primitive" and "one identity chip behind every avatar". For 26 of those commits, the markup that was removed goes in as the state, and all 45 components/ui primitives become the options, each described by its own doc comment.

Jev's first pick is the primitive the commit actually used 7 of 26 times, and it's in the top three 10 of 26 times. At 0.9 confidence or above it's right 7 of 11 times:

  • 40a2637 fix(desktop): scope pane fallback menus to the clicked content: actions-menu at 0.92
  • 1b7e8c4 fix(desktop): every settings row renders through one ListRow/ToggleRow/Slider/SearchField: search-field at 0.97
  • 9ed308f refactor(desktop): one identity chip behind every avatar: avatar-chip at 0.93
  • 5df9cd2 feat(desktop): let ConfirmDialog carry a secondary action: confirm-dialog at 1.00
  • 1e26c02 refactor(desktop): route cron delete and review revert through ConfirmDialog: confirm-dialog at 1.00

That makes it a hint rather than a gate. It reliably catches rebuilt copies of ConfirmDialog, AvatarChip and SearchField, which are the most common kind, and it's cheap enough to run on every component an agent writes. It misses when the right answer depends on what the thing is for, like a fade mask or a log view, rather than how its markup looks. Figma frames have the same problem, so send the frame name and the designer's notes along with the layer tree.

Figma: Figma's Dev Mode MCP serves a frame's layer tree, which would go in state with the kit's components as the options. The question is the same as above. This part is untested, because the MCP needs the Figma desktop app with a file open.

Putting it together

Here's a design-to-code workflow on the Workflows canvas, with Jev at each decision:

Trigger: Figma frame / PR opened
  └─ Gate · Jev choice   which kit components? (≥0.9: pass them as hints)
      └─ Agent           writes the code, using those components
          └─ Gate · Jev noul × DESIGN.md rules   tip on a dismiss button? hand-built dialog?
              ├─ all clear: Agent opens the PR
              ├─ confident violation: Agent fixes it and loops back
              └─ unsure: Human, a designer reviews the flagged spots

What to build first:

  1. The n8n swap (01). Same answers as the Sonnet classifier, much cheaper and faster, and the workflow file imports as it is.
  2. The DESIGN.md linter (02). Each rule becomes one precise noul, run on the diff after every coding agent. It found 4 violations in the current app.
  3. Component hints before generating (05). Put the top three primitive picks into the coding agent's prompt. It's cheap, and it catches the most common kind of drift.
