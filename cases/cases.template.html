Examples

Jev in workflow gates, on real data

The tutorial explains the idea. This page shows how it holds up. Each section takes a decision an automated workflow on a busy open-source repo has to make, and asks Jev to make it on real issues, pull requests and comments. Its answers are checked against what the maintainers actually did, so you can see where it works and where it doesn't.

01 · After an agent step

Did the agent actually finish?

Before a workflow moves on, it needs to know whether the agent's last step worked. A common shortcut is to search the agent's reply for PASS, or check whether it starts with YES. Here are $V_N agent summaries, each checked that way and also put to Jev as one yes/no question: "The step achieved its goal and the work is ready to move on."

$V_ROWS
Step summaryReally doneSubstring ruleJev

The substring rule gets $V_SUB of $V_N wrong. Jev, cutting at 0.5, gets $V_JEV wrong. The rule's mistakes aren't exotic, either. "Should NOT PASS", "PASSED the type check; the runtime still crashes" and "Yes, I looked at it. The approach is wrong" all count as passes. Look at the middle scores too: "I couldn't test Windows" comes back at 0.51, which is exactly the kind of summary you'd want a person to read.

These summaries are written by hand to cover the ways the shortcut fails.

02 · When a pull request opens

Sorting new pull requests

Picture a workflow that runs whenever a pull request opens and sends it one of three ways: straight to the catalog checks, through a light docs review, or to a security reviewer. Jev answers all three questions in one call per pull request. The right answers come from the PRs themselves. A PR counts as catalog-only or docs-only based on the files it touches, and as security-related if a maintainer gave it a security label (type/security, area/auth or sweeper:risk-security-boundary). These are the $G_N most recent pull requests.

"catalog":  "The pull request only adds or updates a plugin-catalog entry and changes
             no application code."
"docs":     "The change only touches documentation and changes no runtime behavior."
"security": "The change alters an authentication, authorization, secret-handling,
             or sandbox boundary."
$G_ROWS
QuestionReally yesSaid yes, rightSaid yes, wrongSaid no, wrongNot sure, sent to a person

The catalog and docs questions are reliable enough to automate now. A catalog-only PR, for instance, could skip the full review agent and go straight to the catalog checks.

The security question works more like a smoke detector. It sends $G_UNS PRs to a person, and $G_UNS_POS of those had a security label. The PRs it said yes to without a label are worth a look:

    $G_FP

Most of them handle credentials or tokens and just never got labelled, so the label is what's missing, not Jev's judgement. For this one, a false alarm costs a reviewer a minute, and a missed one can cost a lot more. Send it to a person, never to auto-merge.

03 · When a pull request opens

Spotting competing PRs

The repo has four known pairs of pull requests that fix the same thing, each flagged by a maintainer or triage bot with a comment like "closing in favour of…". The test mixes those 8 with 30 random ones and one near-miss pair, then asks about each pull request against every other one in the pool. That comes to $D_Q nouls in one request, with no embeddings, no vector store and no pairwise prompts.

questions = {
  str(other.number): {"type": "noul", "instructions": {
      "other_pull_request": {title, description, files},
      "question": "This other pull request fixes the same underlying problem…"}}
  for other in open_prs }

The near miss is the one to look at: two "retry on update" pull requests opened the same afternoon, with almost identical titles, that fix different code paths. Jev gave them 0.12. Anything matching on title similarity would have flagged them.

All of it took $D_CALLS calls and cost $D_COST, about $D_MS ms each, covering every pair in a pool of $D_POOL. In a real workflow, each new pull request would be checked against the open ones in the same area. Above 0.8, an agent step drafts a "possible duplicate of…" comment for a person to post.

04 · When an issue opens

Routing issues to a component

This one is a single choice over the repo's 11 comp/* labels, using each label's GitHub description as the option text. A pick counts as right if it matches any comp/ label a maintainer applied. Across $R_N issues, $R_ACC were right. That headline number is less useful than what the confidence tells you:

$R_BANDS
ConfidenceIssuesRight

A gate that routes automatically at 0.9 or above would handle $R_HI_SHARE of issues at $R_HI_ACC accuracy and pass the rest to the triage agent. Most of its confident misses are reasonable disagreements:

    $R_MISSES

Tune on one set, score on another

A lot of the misses are messaging adapters, which this repo files under comp/plugins. Rewriting the option descriptions to say so seems like an obvious fix. On 150 held-out issues, though, the original descriptions score $H1_ACC ($H1_HI at 0.9 or above) and the rewritten ones score $H2_ACC ($H2_HI). The rewrite only fit the examples it was written from. Keep a separate set of examples for scoring, and don't tune questions on the same examples you measure them with.

05 · Waiting on a person in chat

Reading an approval reply

When a workflow asks someone to approve something, it waits until they reply from chat. A choice question turns that free-text reply into something the run can act on. The conditional and question options do the most work here, because they stop "yes but fix the typo first" from counting as a plain yes.

$A_ROWS
ReplyRead asConfidence

All $A_N replies are read the way a person would read them, "ok" included. "idk ask the lead" comes back as unclear at 0.75, below the line for acting automatically, which is what you want. In a workflow, approve at 0.9 or above resumes the run, reject stops it, and anything else asks again with the reply quoted.

These replies are written by hand.

06 · When someone comments

Waking an agent only for comments that matter

Long issue threads fill up with +1s, bot output and closing notes. This test asks three nouls in one call about each of the $C_N most recent comments in the repo: does it add new evidence, is it automated, and does it close or supersede something?

$C_ROWS
CommentNew evidenceBotClosing

$C_WAKE of $C_N comments would wake an agent to re-investigate (evidence at 0.8 or above, and not automated). Every one of them is a reproduction or a measurement from someone's machine: Windows confirmations, OOM-kill rates, a 180-message repro on a branch. The $C_CLOSE closing notes could mark an issue as superseded without running an agent at all.

Jev answers the question you actually asked. Comments written by an agent often read as careful prose, so they score low on "automated". If you mean "was this written by an agent", ask that as its own question.

07 · Where it doesn't work

Where it falls short: priority

Here Jev was asked to place each bug on the repo's P3 to P0 scale with a score question. Across $P_N labelled bugs it matched the exact label only $P_EXACT of the time, and its average score barely tells P3 and P2 apart:

$P_ROWS
LabelBugsMean score (0 = P3, 3 = P0)

It's still useful for ordering a queue. A random P1 outscores a random non-P1 $P_AUC1 of the time, where 0.5 would be a coin flip. The top of its list is the right kind of bug:

    $P_TOP

So use it to sort the queue, not to set the label. Whether something is P2 or P3 here mostly depends on things that aren't in the issue: how many people hit it, what's shipping this week, which maintainer picked it up. Jev can only judge what you send it, and the issue text doesn't contain that answer. Splitting the scale into six separate nouls and weighting them, which is the approach TypeSafe recommends, barely moved it either ($P_ATOM against $P_AUC1).

What to build first

  1. Step verdicts (01). It fixes a real bug in the runner, and every gate benefits.
  2. Competing-PR detection (03) on PR intake. It separated every pair here, and it's the one that saves maintainers the most time.
  3. Approval replies (05) for the Human step. Without it, a reply from chat can't move the run forward at all.
