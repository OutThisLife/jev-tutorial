Examples

Jev in workflow gates, tried on real Hermes data

The tutorial explains the idea. This page shows how it holds up. Each section takes one decision a Hermes workflow makes, or could make, and asks Jev to make it on real issues, PRs and comments from NousResearch/hermes-agent. Its answers are checked against what maintainers actually did, so you can see both where it works and where it doesn't.

$CALLS calls · $COST in total · $MS ms median per call · model typesafe/jev-1.14 via OpenRouter. The code and raw results are in cases/.
01 · Agent step, then a gate

Did the step actually work?

Every gate starts from a verdict on the step before it. When an agent step doesn't return an explicit verdict, the current runner decides by searching the reply for PASS, or checking whether it starts with YES. To see how that compares, here are $V_N step summaries, each put to Jev as one noul: "The step achieved its goal and the work is ready to move on."

$V_ROWS
Step summaryReally doneSubstring ruleJev

The substring rule gets $V_SUB of $V_N wrong. Jev, cutting at 0.5, gets $V_JEV wrong. The rule's mistakes aren't exotic, either. "Should NOT PASS", "PASSED the type check; the runtime still crashes" and "Yes, I looked at it. The approach is wrong" all count as passes. Look at the middle scores too: "I couldn't test Windows" comes back at 0.51, which is exactly the kind of summary you'd want a person to read.

These summaries are written by hand to cover the ways the rule fails. The rule itself is copied from _arm_matches.

02 · Webhook (PR opened), then a gate

Gate arms on real PRs

Picture a PR-intake workflow whose gate has three Judgement arms, all asked in one call per PR. The right answers come from the PRs themselves. A PR counts as catalog-only or docs-only based on the files it touches, and as security-related if a maintainer gave it a security label (type/security, area/auth or sweeper:risk-security-boundary). These are the $G_N most recent PRs.

"catalog":  "The pull request only adds or updates a plugin-catalog entry and changes
             no Hermes code."
"docs":     "The change only touches documentation and changes no runtime behavior."
"security": "The change alters an authentication, authorization, secret-handling,
             or sandbox boundary."
$G_ROWS
ArmReally yesTook, rightTook, wrongSkipped, wrongUnsure, sent to a person

The catalog and docs arms are reliable enough to automate now. A catalog-only PR, for instance, could skip the full review agent and go straight to the catalog checks.

The security arm works more like a smoke detector. It sends $G_UNS PRs to a person, and $G_UNS_POS of those had a security label. The PRs it said yes to without a label are worth a look:

    $G_FP

Most of them handle credentials or tokens and just never got labelled, so the label is what's missing, not Jev's judgement. For this arm, a false alarm costs a reviewer a minute, and a missed one can cost a lot more. Send it to a person, never to auto-merge.

03 · Webhook (PR opened), then an agent comment

Spotting competing PRs

The repo has four known pairs of PRs that fix the same thing, each flagged by a maintainer or triage bot with a comment like "closing in favour of…". The test mixes those 8 PRs with 30 random ones and one near-miss pair, then asks each PR a single question about every other PR in the pool. That comes to $D_Q nouls in one request, with no embeddings, no vector store and no pairwise prompts.

questions = {
  str(other.number): {"type": "noul", "instructions": {
      "other_pull_request": {title, description, files},
      "question": "This other pull request fixes the same underlying problem…"}}
  for other in open_prs }
$D_ROWS
PRsTitlesJev

Every real pair scored higher than every unrelated one. The lowest real duplicate scored $D_MIN, and the highest unrelated pair scored $D_MAX. The near miss is the one to look at: two "retry on update" PRs opened the same afternoon, with almost identical titles, that fix different code paths. Jev gave them 0.12. Anything matching on title similarity would have flagged them.

All of it took $D_CALLS calls and cost $D_COST, about $D_MS ms each, covering every pair in a $D_POOL-PR pool. In a real workflow, a new PR would ask one question per open PR in the same component. Above 0.8, an agent step drafts a "possible duplicate of…" comment for a person to post.

04 · Webhook (issue opened), then a gate, then an agent per component

Routing issues to a component

This one is a single choice over the repo's 11 comp/* labels, using each label's GitHub description as the option text. A pick counts as right if it matches any comp/ label a maintainer applied. Across $R_N issues, $R_ACC were right. That headline number is less useful than what the confidence tells you:

$R_BANDS
ConfidenceIssuesRight

A gate that routes automatically at 0.9 or above would handle $R_HI_SHARE of issues at $R_HI_ACC accuracy and pass the rest to the triage agent. Most of its confident misses are reasonable disagreements:

    $R_MISSES

Tune on one set, score on another

A lot of the misses are messaging adapters, which this repo files under comp/plugins. Rewriting the option descriptions to say so seems like an obvious fix. On 150 held-out issues, though, the original descriptions score $H1_ACC ($H1_HI at 0.9 or above) and the rewritten ones score $H2_ACC ($H2_HI). The rewrite only fit the examples it was written from. Keep a separate set of examples for scoring, and don't tune questions on the same examples you measure them with.

05 · Human step (reply from Telegram, Slack or Discord)

Reading an approval reply

A Human step waits until someone replies from chat. A choice question turns that free-text reply into something the run can act on. The conditional and question options do the most work here, because they stop "yes but fix the typo first" from counting as a plain yes.

$A_ROWS
ReplyRead asConfidence

All $A_N replies are read the way a person would read them, "ok" included. "idk ask teknium" comes back as unclear at 0.75, below the line for acting automatically, which is what you want. In a workflow, approve at 0.9 or above resumes the run, reject stops it, and anything else asks again with the reply quoted.

These replies are written by hand.

06 · Event trigger (issue comment), then an agent

Waking an agent only for comments that matter

Long issue threads fill up with +1s, bot output and closing notes. This test asks three nouls in one call about each of the $C_N most recent comments in the repo: does it add new evidence, is it automated, and does it close or supersede something?

$C_ROWS
AuthorCommentEvidenceBotClosing

$C_WAKE of $C_N comments would wake an agent to re-investigate (evidence at 0.8 or above, and not automated). Every one of them is a reproduction or a measurement from someone's machine: Windows confirmations, OOM-kill rates, a 180-message repro on a branch. The $C_CLOSE closing notes could mark an issue as superseded without running an agent at all.

LordMelkor's comments starting with 🤖 are written by an agent, but they score low on "automated" because they read as thoughtful prose. Jev answers the question you actually asked. If you mean "was this written by an agent", ask that directly.

07 · Where it doesn't work

Where it falls short: priority

Here Jev was asked to place each bug on the repo's P3 to P0 scale with a score question. Across $P_N labelled bugs it matched the exact label only $P_EXACT of the time, and its average score barely tells P3 and P2 apart:

$P_ROWS
LabelBugsMean score (0 = P3, 3 = P0)

It's still useful for ordering a queue. A random P1 outscores a random non-P1 $P_AUC1 of the time, where 0.5 would be a coin flip. The top of its list is the right kind of bug:

    $P_TOP

So use it to sort the queue, not to set the label. Whether something is P2 or P3 here mostly depends on things that aren't in the issue: how many people hit it, what's shipping this week, which maintainer picked it up. Jev can only judge what you send it, and the issue text doesn't contain that answer. Splitting the scale into six separate nouls and weighting them, which is the approach TypeSafe recommends, didn't help either (0.80 against 0.79).

The data in cases/data/ was pulled with gh on Oct 15.

What to build first

  1. Step verdicts (01). It fixes a real bug in the runner, and every gate benefits.
  2. Competing-PR detection (03) on PR intake. It separated every pair here, and it's the one that saves maintainers the most time.
  3. Approval replies (05) for the Human step. Without it, a reply from chat can't move the run forward at all.
