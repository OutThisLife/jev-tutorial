Examples

Jev in workflow gates, on real data

Each section is a decision an automated workflow on a busy open-source repo has to make. Jev makes it on real issues, pull requests and comments, and its answers are checked against what the maintainers actually did.

$CALLS calls · $COST in total · $MS ms median per call · model typesafe/jev-1.14 via OpenRouter. The code and raw results are in cases/.
01 · After an agent step

Did the agent actually finish?

A common shortcut for "did the agent finish?" is to search its reply for PASS or check whether it starts with YES. Here are $V_N agent summaries, checked that way and put to Jev as one yes/no question: "The step achieved its goal and the work is ready to move on."

$V_ROWS
Step summaryReally doneSubstring ruleJev

The substring rule gets $V_SUB of $V_N wrong. Jev, cutting at 0.5, gets $V_JEV wrong. "Should NOT PASS", "PASSED the type check; the runtime still crashes" and "Yes, I looked at it. The approach is wrong" all pass the substring check. Jev's middle scores are useful too: "I could not test Windows" gets 0.51, exactly what a person should read.

The summaries are hand-written.

02 · When a pull request opens

Sorting new pull requests

A workflow sends each new pull request one of three ways: catalog checks, a light docs review, or a security reviewer. Jev answers all three questions in one call per pull request. The right answers come from the files each one touches, and from maintainers' security labels (type/security, area/auth, sweeper:risk-security-boundary). These are the $G_N most recent.

"catalog":  "The pull request only adds or updates a plugin-catalog entry and changes
             no application code."
"docs":     "The change only touches documentation and changes no runtime behavior."
"security": "The change alters an authentication, authorization, secret-handling,
             or sandbox boundary."
$G_ROWS
QuestionReally yesSaid yes, rightSaid yes, wrongSaid no, wrongNot sure, sent to a person

Catalog and docs are reliable enough to automate. A catalog-only pull request could skip the full review and go straight to the catalog checks.

Security works like a smoke detector. It sends $G_UNS to a person ($G_UNS_POS of them labelled security). The ones it called security without a label:

    $G_FP

Most handle credentials or tokens and simply weren't labelled. A false alarm costs a reviewer a minute and a miss costs far more, so send this one to a person, never to auto-merge.

03 · When a pull request opens

Spotting competing PRs

The repo has four known pairs of pull requests that fix the same thing, each flagged by a maintainer with a comment like "closing in favour of…". Mixed with 30 random ones and one near-miss pair, each pull request is asked about every other: $D_Q nouls in one request, with no embeddings or vector store.

questions = {
  str(other.number): {"type": "noul", "instructions": {
      "other_pull_request": {title, description, files},
      "question": "This other pull request fixes the same underlying problem…"}}
  for other in open_prs }
$D_ROWS
The two pull requestsJev

Every real pair scored above every unrelated one: lowest real $D_MIN, highest unrelated $D_MAX. The near miss is two "retry on update" pull requests from the same afternoon, with near-identical titles, fixing different code. Jev gave them 0.12; a title matcher would have flagged them.

That took $D_CALLS calls, $D_COST, about $D_MS ms each. In a workflow, each new pull request gets checked against open ones in the same area, and anything above 0.8 gets a drafted "possible duplicate" comment for a person to post.

04 · When an issue opens

Routing issues to a component

One choice over the repo's 11 comp/* labels, with each label's description as the option. A pick is right if it matches any label a maintainer applied. $R_ACC of $R_N issues were right, but the confidence tells you more:

$R_BANDS
ConfidenceIssuesRight

Routing automatically at 0.9 or above handles $R_HI_SHARE of issues at $R_HI_ACC accuracy. Its confident misses are mostly reasonable disagreements:

    $R_MISSES

Tune on one set, score on another

Many misses are messaging adapters, which this repo files under comp/plugins, so rewriting the descriptions to say that seems obvious. On 150 held-out issues, though, the originals score $H1_ACC ($H1_HI at 0.9+) and the rewrite $H2_ACC ($H2_HI). It only fit the examples it was written from, so score questions on examples you didn't tune them on.

05 · Waiting on a person in chat

Reading an approval reply

A workflow waiting on approval gets a free-text reply from chat. One choice turns it into something the run can act on. The conditional and question options stop "yes but fix the typo first" from counting as a yes.

$A_ROWS
ReplyRead asConfidence

All $A_N read the way a person would, "ok" included. "idk ask the lead" comes back unclear at $A_LEAD, below the auto-act line. In a workflow, approve at 0.9+ resumes, reject stops, and anything else asks again.

The replies are hand-written.

06 · When someone comments

Waking an agent only for comments that matter

Threads fill up with +1s, bot output and closing notes. Three nouls in one call, on each of the $C_N most recent comments: does it add evidence, is it automated, does it close something?

$C_ROWS
CommentNew evidenceBotClosing

$C_WAKE of $C_N comments would wake an agent (evidence 0.8+, not automated), and every one is a repro or measurement. The $C_CLOSE closing notes could mark issues superseded without an agent at all.

Jev answers the question you asked. Agent-written comments read as careful prose, so they score low on "automated"; to catch them, ask "was this written by an agent?".

07 · Where it doesn't work

Where it falls short: priority

A score question placed each bug on the repo's P3–P0 scale. Across $P_N labelled bugs it hit the exact label only $P_EXACT of the time, and barely told P3 from P2:

$P_ROWS
LabelBugsMean score (0 = P3, 3 = P0)

It still sorts well: a random P1 outscores a random non-P1 $P_AUC1 of the time (0.5 is a coin flip), and the top of its list is the right kind of bug:

    $P_TOP

Use it to sort the queue, not set the label. P2 versus P3 mostly depends on things the issue text doesn't contain, like how many people hit it. Six weighted nouls, TypeSafe's recommended approach, didn't help either ($P_ATOM against $P_AUC1).
