Seven jobs for Jev, run on real Hermes data

Each case is a decision your workflows already make, or could make, with an agent step today. Every number below comes from live Jev calls against real NousResearch/hermes-agent issues, PRs and comments, scored against the labels maintainers actually applied.

$CALLS live calls · $COST total · $MS ms median per call · model typesafe/jev-1.14 via OpenRouter. Code and raw results are in cases/.
01 · Agent step → Gate

Did the step actually work?

Every gate starts from a verdict on the step before it. When an agent step doesn't return an explicit verdict, today's runner searches its reply for PASS, or a reply that starts with YES. Here are $V_N step summaries, each asked as one Noul: "The step achieved its goal and the work is ready to move on."

$V_ROWS
Step summaryReally doneSubstring ruleJev

The substring rule gets $V_SUB of $V_N wrong; Jev at 0.5 gets $V_JEV wrong. The substring misses aren't edge cases: "should NOT PASS", "PASSED the type check; the runtime still crashes" and "Yes, I looked at it. The approach is wrong" all pass. The unsure ones are useful too: "I couldn't test Windows" lands at 0.51, exactly the kind of summary a person should look at.

Summaries are synthetic, written to cover the failure modes. The substring rule is _arm_matches verbatim.

02 · Webhook (PR opened) → Gate

Gate arms on real PRs

A PR-intake workflow with three Judgement arms, all asked in one call per PR. Ground truth comes from the PR itself: its files (only plugin-catalog/, only .md/website/), or a security label a maintainer applied (type/security, area/auth, sweeper:risk-security-boundary). These are the $G_N most recent PRs.

"catalog":  "The pull request only adds or updates a plugin-catalog entry and changes
             no Hermes code."
"docs":     "The change only touches documentation and changes no runtime behavior."
"security": "The change alters an authentication, authorization, secret-handling,
             or sandbox boundary."
$G_ROWS
ArmReally yesTook, rightTook, wrongSkipped, wrongUnsure → human

Catalog and docs are clean enough to automate today. For example, a catalog-only PR could skip the full review agent and go straight to the catalog checks.

Security behaves like a smoke detector. It sends $G_UNS PRs to a human ($G_UNS_POS of them labelled security). Its "wrong" yes answers are worth reading:

    $G_FP

Most of these handle credentials or tokens and simply never got a security label. That makes them misses in the labels, not mistakes by Jev. For a security arm, a false alarm costs a minute of a reviewer's time; a missed real one costs far more. Wire this arm to a human, never to auto-merge.

03 · Webhook (PR opened) → Agent (comment)

Spot competing PRs

The repo has four known pairs of PRs that fix the same thing. Maintainers or triage bots flagged them in comments like "closing in favour of…". I mixed those 8 PRs with 30 random others and a near-miss pair, then asked each PR one question about every other PR in the pool: $D_Q Nouls in a single request, with no embeddings, vector store or pairwise prompts.

questions = {
  str(other.number): {"type": "noul", "instructions": {
      "other_pull_request": {title, description, files},
      "question": "This other pull request fixes the same underlying problem…"}}
  for other in open_prs }
$D_ROWS
PRsTitlesJev

Perfect separation. The lowest real duplicate scored $D_MIN; the highest unrelated pair scored $D_MAX. The near miss is the impressive one: two "retry on update" PRs from the same afternoon, with almost the same titles, that fix different code paths. Jev put them at 0.12. A title-similarity bot would have flagged them.

Cost: $D_CALLS calls, $D_COST, about $D_MS ms each, for every pair in a $D_POOL-PR pool. In a workflow, a new PR asks one question per open PR in the same component. When the score is above 0.8, an agent step drafts the "possible duplicate of…" comment for a human to post.

04 · Webhook (issue opened) → Gate → Agent per component

Route issues to a component

One Choice over the repo's 11 comp/* labels, using the label descriptions from GitHub as the options. A pick counts as right if it matches any of the issue's maintainer-applied comp/ labels. That's $R_N issues, and $R_ACC were right overall, but the overall number isn't the useful part. The useful part is what the confidence tells you:

$R_BANDS
ConfidenceIssuesRight

A gate that auto-routes at 0.9 or higher handles $R_HI_SHARE of issues at $R_HI_ACC accuracy and sends the rest to the triage agent. Its confident misses are mostly reasonable disagreements:

    $R_MISSES

Tune on one set, score on another

Many misses are messaging adapters, which this repo files under comp/plugins. Rewriting the option descriptions to say so looks like an obvious fix. On 150 held-out issues, though, the original descriptions score $H1_ACC ($H1_HI at 0.9 or higher), and the "improved" ones score $H2_ACC ($H2_HI). The rewrite was fitted to the misses it was written from. Keep a held-out set, and don't tune questions on the examples you score them with.

05 · Human step (reply from Telegram/Slack/Discord)

Read an approval reply

The Human step parks until someone answers from a chat. A Choice turns the free-text reply into something the run can act on. The conditional and question options matter most: they keep "yes but fix the typo first" from counting as a yes.

$A_ROWS
ReplyRead asConfidence

All $A_N replies are read the way a person would read them, including "ok". "idk ask teknium" comes back as unclear at 0.75, below the auto-act line, which is right. In the workflow, approve at 0.9 or higher resumes the run, reject stops it, and everything else re-asks with the reply quoted.

Replies are synthetic.

06 · Event trigger (issue comment) → Agent

Wake an agent only when evidence arrives

Long issue threads mostly fill up with +1s, bot output and closing notes. Three Nouls in one call, on each of the $C_N most recent comments in the repo: does it add new evidence, is it automated, and does it close or supersede something?

$C_ROWS
AuthorCommentEvidenceBotClosing

$C_WAKE of $C_N comments would wake a re-investigation agent (evidence 0.8 or higher, not automated). Every one of them is a reproduction or a field measurement: Windows confirmations, OOM-kill rates, a 180-message branch repro. The $C_CLOSE closing notes could update a "superseded" state without running an agent.

One wrinkle: LordMelkor's 🤖-prefixed comments are agent-written, but they score low on "automated" because they read as considered prose. Jev answers the question you asked. If what you really mean is "was this written by an agent", ask that as its own question.

07 · The negative result

Where it falls short: priority

Score was asked to place each bug on the repo's P3 to P0 rubric. On $P_N labeled bugs it hit the exact label only $P_EXACT of the time, and its average score barely separates P3 from P2:

$P_ROWS
LabelBugsMean score (0 = P3, 3 = P0)

For ranking, though, it's useful: a random P1 outscores a random non-P1 $P_AUC1 of the time (0.5 would be chance). The top of the list is the right kind of bug:

    $P_TOP

So use it to sort the queue, not to set the label. P2 versus P3 here mostly depends on things that aren't in the issue text: how many people are affected, what's shipping this week, which maintainer picked it up. Jev can only judge what's in the state you send it, and here the state doesn't contain the answer. Splitting the rubric into six separate Noul questions combined with weights (TypeSafe's recommended "atomic questions" approach) didn't help either: 0.80 versus 0.79.

Build order

  1. Step verdicts (01). This fixes a real bug in the runner, and every gate benefits.
  2. Competing-PR detection (03) on PR intake. It separated the pairs perfectly here, and it saves maintainers the most time.
  3. Approval replies (05) for the Human step. Without it, a reply from chat can't drive the run at all.
