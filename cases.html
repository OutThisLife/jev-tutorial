Examples

Jev in workflow gates, on real data

The tutorial explains the idea. This page shows how it holds up. Each section takes a decision an automated workflow on a busy open-source repo has to make, and asks Jev to make it on real issues, pull requests and comments. Its answers are checked against what the maintainers actually did, so you can see where it works and where it doesn't.

926 calls · $0.046 in total · 178 ms median per call · model typesafe/jev-1.14 via OpenRouter. The code and raw results are in cases/.
01 · After an agent step

Did the agent actually finish?

Before a workflow moves on, it needs to know whether the agent's last step worked. A common shortcut is to search the agent's reply for PASS, or check whether it starts with YES. Here are 10 agent summaries, each checked that way and also put to Jev as one yes/no question: "The step achieved its goal and the work is ready to move on."

The substring rule gets 6 of 10 wrong. Jev, cutting at 0.5, gets 0 wrong. The rule's mistakes aren't exotic, either. "Should NOT PASS", "PASSED the type check; the runtime still crashes" and "Yes, I looked at it. The approach is wrong" all count as passes. Look at the middle scores too: "I couldn't test Windows" comes back at 0.51, which is exactly the kind of summary you'd want a person to read.

These summaries are written by hand to cover the ways the shortcut fails.

02 · When a pull request opens

Sorting new pull requests

Picture a workflow that runs whenever a pull request opens and sends it one of three ways: straight to the catalog checks, through a light docs review, or to a security reviewer. Jev answers all three questions in one call per pull request. The right answers come from the PRs themselves. A PR counts as catalog-only or docs-only based on the files it touches, and as security-related if a maintainer gave it a security label (type/security, area/auth or sweeper:risk-security-boundary). These are the 160 most recent pull requests.

"catalog":  "The pull request only adds or updates a plugin-catalog entry and changes
             no application code."
"docs":     "The change only touches documentation and changes no runtime behavior."
"security": "The change alters an authentication, authorization, secret-handling,
             or sandbox boundary."
QuestionReally yesSaid yes, rightSaid yes, wrongSaid no, wrongNot sure, sent to a person
Catalog only1512006
Docs only42013
Security boundary13114129

The catalog and docs questions are reliable enough to automate now. A catalog-only PR, for instance, could skip the full review agent and go straight to the catalog checks.

The security question works more like a smoke detector. It sends 29 PRs to a person, and 1 of those had a security label. The PRs it said yes to without a label are worth a look:

  • feat(providers): let provider plugins claim tenant-scoped endpoint hosts (0.94)
  • fix(whatsapp): handle locked session dir on re-pair and reject empty creds in preflight (0.84)
  • fix(agent): preserve custom provider headers for auto titles (0.86)

Most of them handle credentials or tokens and just never got labelled, so the label is what's missing, not Jev's judgement. For this one, a false alarm costs a reviewer a minute, and a missed one can cost a lot more. Send it to a person, never to auto-merge.

03 · When a pull request opens

Spotting competing PRs

The repo has four known pairs of pull requests that fix the same thing, each flagged by a maintainer or triage bot with a comment like "closing in favour of…". The test mixes those 8 with 30 random ones and one near-miss pair, then asks about each pull request against every other one in the pool. That comes to 39 nouls in one request, with no embeddings, no vector store and no pairwise prompts.

questions = {
  str(other.number): {"type": "noul", "instructions": {
      "other_pull_request": {title, description, files},
      "question": "This other pull request fixes the same underlying problem…"}}
  for other in open_prs }

Every real pair scored higher than every unrelated one. The lowest real duplicate scored 0.82, and the highest unrelated pair scored 0.16. The near miss is the one to look at: two "retry on update" pull requests opened the same afternoon, with almost identical titles, that fix different code paths. Jev gave them 0.12. Anything matching on title similarity would have flagged them.

All of it took 10 calls and cost $0.0077, about 283 ms each, covering every pair in a pool of 40. In a real workflow, each new pull request would be checked against the open ones in the same area. Above 0.8, an agent step drafts a "possible duplicate of…" comment for a person to post.

04 · When an issue opens

Routing issues to a component

This one is a single choice over the repo's 11 comp/* labels, using each label's GitHub description as the option text. A pick counts as right if it matches any comp/ label a maintainer applied. Across 150 issues, 90% were right. That headline number is less useful than what the confidence tells you:

ConfidenceIssuesRight
0.9 or higher8795%
0.6 to 0.94183%
below 0.62282%

A gate that routes automatically at 0.9 or above would handle 58% of issues at 95% accuracy and pass the rest to the triage agent. Most of its confident misses are reasonable disagreements:

  • Public subagent lifecycle re-truncates native summaries and drops spill recovery metadata: picked comp/agent at 1.00; the maintainers chose comp/plugins
  • [Bug]: Streaming STT resampler adds samples when 44.1 kHz audio arrives in chunks: picked comp/tools at 0.98; the maintainers chose comp/desktop
  • browser_tool_session: redact daemon output, and let a provider opt out of the local Chromium fallback: picked comp/tools at 0.96; the maintainers chose comp/agent
  • [Bug]: A2A inbound silently rejects all peers (403) when bound to 0.0.0.0 and no trusted peers configured: picked comp/acp at 0.89; the maintainers chose comp/plugins

Tune on one set, score on another

A lot of the misses are messaging adapters, which this repo files under comp/plugins. Rewriting the option descriptions to say so seems like an obvious fix. On 150 held-out issues, though, the original descriptions score 87% (92% at 0.9 or above) and the rewritten ones score 85% (90%). The rewrite only fit the examples it was written from. Keep a separate set of examples for scoring, and don't tune questions on the same examples you measure them with.

05 · Waiting on a person in chat

Reading an approval reply

When a workflow asks someone to approve something, it waits until they reply from chat. A choice question turns that free-text reply into something the run can act on. The conditional and question options do the most work here, because they stop "yes but fix the typo first" from counting as a plain yes.

All 16 replies are read the way a person would read them, "ok" included. "idk ask the lead" comes back as unclear at 0.75, below the line for acting automatically, which is what you want. In a workflow, approve at 0.9 or above resumes the run, reject stops it, and anything else asks again with the reply quoted.

These replies are written by hand.

06 · When someone comments

10 of 40 comments would wake an agent to re-investigate (evidence at 0.8 or above, and not automated). Every one of them is a reproduction or a measurement from someone's machine: Windows confirmations, OOM-kill rates, a 180-message repro on a branch. The 13 closing notes could mark an issue as superseded without running an agent at all.

Jev answers the question you actually asked. Comments written by an agent often read as careful prose, so they score low on "automated". If you mean "was this written by an agent", ask that as its own question.

07 · Where it doesn't work

Where it falls short: priority

Here Jev was asked to place each bug on the repo's P3 to P0 scale with a score question. Across 120 labelled bugs it matched the exact label only 40% of the time, and its average score barely tells P3 and P2 apart:

LabelBugsMean score (0 = P3, 3 = P0)
P3361.55
P2791.58
P152.11

It's still useful for ordering a queue. A random P1 outscores a random non-P1 0.79 of the time, where 0.5 would be a coin flip. The top of its list is the right kind of bug:

  • session.list crash-loops when a live session's DB row is gone (TypeError in session_authority._h (P2, 2.97)
  • execute_code: a nested tool call outlives its cell and applies a protected-file write after the (P2, 2.87)
  • Kanban dispatcher kills worker PID from DB without verifying process identity (PID reuse can hit (P3, 2.85)
  • Windows: interrupted source-update auto-repair loops on every launch (sync-stage failures bypass (P2, 2.83)
  • Anthropic 'credentials are rate-limited for <model>' AuthError has no code, so a kanban worker e (P3, 2.73)
  • Public subagent lifecycle re-truncates native summaries and drops spill recovery metadata (P3, 2.69)

So use it to sort the queue, not to set the label. Whether something is P2 or P3 here mostly depends on things that aren't in the issue: how many people hit it, what's shipping this week, which maintainer picked it up. Jev can only judge what you send it, and the issue text doesn't contain that answer. Splitting the scale into six separate nouls and weighting them, which is the approach TypeSafe recommends, barely moved it either (0.79 against 0.79).

What to build first

  1. Step verdicts (01). It fixes a real bug in the runner, and every gate benefits.
  2. Competing-PR detection (03) on PR intake. It separated every pair here, and it's the one that saves maintainers the most time.
  3. Approval replies (05) for the Human step. Without it, a reply from chat can't move the run forward at all.
