Use cases · n8n · design systems

Jev for n8n, design-to-code, and design systems

Something gets made, by an agent or a person, and then a small judgement call decides what happens next. Jev makes that call in about 200 ms and says how sure it is. Below the confidence line, a person or a bigger model takes over.

Data: n8n's public template library, the Hermes desktop UI kit (components/ui), its DESIGN.md, and its git history · $CALLS Jev calls, $COST · code and results in design/

The shape of it

Jev doesn't draw or write code, and it can only pick from options you give it. It answers small multiple-choice questions about things that already exist, for roughly the cost of a log line. So it doesn't replace the model that writes the code. It sits at the decision points around it:

MomentThe questionType
Before generatingWhich existing component should this frame become?choice over the kit
While generatingWhich variant / token / icon fits this spot?choice
After generatingDoes this break a rule in DESIGN.md?noul per rule
In n8nWhich branch does this item take?choice → Switch
01 · n8n

Swap the LLM classifier for one HTTP node

The most common AI shape in n8n's template library is trigger → LLM classifier → parse JSON → Switch. In “Classify and route DevOps chat requests with Mattermost and Claude”, the classifier is a Sonnet agent with a $N_PROMPT-character system prompt. After it comes an 85-line Code node that pulls the JSON out of code fences, falls back to other when parsing fails, and re-checks that the category is valid.

Jev takes the template's $N_CATS category descriptions as its options. On $N_N new DevOps messages (none of them the template's own examples):

RightMedian timeCost for all $N_N
Template's Sonnet classifier$N_LLM / $N_N$N_LLM_MS$N_LLM_COST
One Jev Choice$N_JEV / $N_N$N_JEV_MS ms$N_JEV_COST

Same accuracy, about $N_RATIO× cheaper, about $N_SPEED× faster, and no parser. The response already has the shape the Switch reads. The three least confident answers were the three genuinely borderline messages, which is where an "Ask a human" branch belongs:

    $N_LOW

Drop-in workflow

design/n8n/jev-router.json imports straight into n8n: Webhook → Set → HTTP Request to Jev → Set → If (confidence ≥ 0.6) → Switch, with the low-confidence branch going to "Ask a human". The Jev node takes about $S_MS ms. For the sample message about a deploy stuck waiting for a runner, it returns $S_CAT at $S_CONF.

// the whole "AI" part of the workflow: an HTTP Request node
POST https://openrouter.ai/api/v1/systemone
{ "model": "~typesafe/jev-latest",
  "state": { "message": "{{ $$json.message }}" },
  "questions": { "category": { "type": "choice", "criteria": { …the template's categories… } } } }
// Switch on {{ $$json.answers.category.choice }}; If on .confidence

n8n's built-in Text Classifier node does the same job with any chat model, but it doesn't return a confidence. The best it can do with an unclear item is drop it or send it to an "Other" branch. Jev's probabilities are what make a real "ask a human" branch possible.

02 · Design system · lint

Lint the rules a regex can't

Hermes' DESIGN.md has rules like “Do not tip menu triggers” and “Do not tip close / dismiss X buttons — the glyph is the label”. A regex can't tell what a button is for. Two yes/no questions per <Tip> can: "is this control a close/dismiss button?" and "does it open a menu?". Across all $T_N Tips in the desktop app:

$T_ROWS
TooltipRule it breaksJevWhere

All $T_V are real violations. “Clear search” is inside SearchField, so every search box in the app inherits it. A third question, "does hover teach something new?", gives muddy scores. That one depends on what's already visible around the control, and the snippet doesn't show that. Keep the precise questions in the linter and leave the fuzzy one to a human reviewer.

In a workflow, this runs after the coding agent and before the PR: one call per changed Tip. Anything at 0.8 or higher becomes a review comment that quotes the DESIGN.md line.

03 · Design system · iconography

Does the icon say what the label says?

DESIGN.md says to “reuse the existing icon for an action.” One Noul per icon-only button checks whether the icon clearly communicates its aria-label. Of the app's $I_N icon/label pairs, $I_OK score 0.8 or higher, e.g. $I_HIGH. These are the lowest scores:

$I_LOW
IconLabelFitsJev would pickWhere

Treat these as review candidates, not bugs. The clearest one is "New branch" on a kebab icon: the button opens the branch menu, but the icon says "more". The four discard rows are a naming question rather than a defect. The app consistently uses discard for revert and reset, while Jev's general instinct is refresh. Writing that convention into DESIGN.md once would stop the next agent from guessing.

05 · Design → code · before generating

“Build this on the existing component”

The most common way a design system drifts is a hand-built copy of a component that already exists. The git history has plenty of commits fixing that, e.g. “build the task modal on the shared Dialog primitive” and “one identity chip behind every avatar”. For $P_N of those commits, the markup that was removed goes in as state, and all $P_OPTS components/ui primitives become the options, each described by its own doc comment.

Jev picks the primitive the commit actually used first $P_TOP1 of $P_N times, and has it in its top three $P_TOP3 of $P_N times. At 0.9 confidence or higher it's right $P_HI_OK of $P_HI times:

    $P_WINS

That makes it a hint, not a gate. It reliably catches rebuilt copies of ConfirmDialog, AvatarChip and SearchField, which are the most common kind, and it's cheap enough to run on every component an agent writes. The misses are components where the right answer depends on what the thing is for (a fade mask, a log view) rather than how its markup looks. Figma frames have the same limitation, so send the frame name and the designer's notes along with the layer tree.

Figma: Figma's Dev Mode MCP serves a frame's layer tree. That tree goes in state, with the kit's components as the options. The question is the same as in the commit-history test above. That part is untested, because the MCP needs the Figma desktop app with a file open.

Where it goes

A design-to-code workflow on the Workflows canvas, with Jev at each decision point:

Trigger: Figma frame / PR opened
  └─ Gate · Jev choice   which kit components? (≥0.9 → pass them as hints)
      └─ Agent           writes the code, using those components
          └─ Gate · Jev noul × DESIGN.md rules   tip on a dismiss button? hand-rolled dialog?
              ├─ all clear  → Agent opens the PR
              ├─ confident violation → Agent fixes it, loops back
              └─ unsure → Human: designer reviews the flagged spots

Build order:

  1. The n8n swap (01). Same answers as the Sonnet classifier, far cheaper and faster. The workflow file imports as-is.
  2. The DESIGN.md linter (02). Each rule becomes a precise Noul, run on the diff after every coding agent. It found 4 violations in the current app.
  3. Component hints before generating (05). Put the top three primitive picks into the coding agent's prompt. It's cheap and catches the most common kind of drift.
