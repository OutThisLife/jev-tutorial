Jev in n8n and design systems

Something gets made, by an agent or a person, and a small call decides what happens next: which n8n branch, which component, whether a button breaks a rule. Jev makes those calls in about 200 ms and says how sure it is, so a person or a bigger model only steps in when it isn't.

Data: n8n's public template library, plus a real desktop app's UI kit (components/ui), its design rules (DESIGN.md) and its git history · $CALLS Jev calls, $COST · the code and results are in design/

Where it fits

Jev doesn't write code. It answers small multiple-choice questions about things that already exist, so it handles the decisions around the model that does:

WhenThe questionType
Before generatingWhich existing component should this frame become?choice over the kit
While generatingWhich variant, token or icon fits this spot?choice
After generatingDoes this break a rule in DESIGN.md?noul per rule
In n8nWhich branch does this item take?choice, feeding a Switch
01 · n8n

Swapping the LLM classifier for one HTTP node

The most common AI pattern in n8n's templates is trigger, LLM classifier, parse JSON, Switch. In "Classify and route DevOps chat requests with Mattermost and Claude", the classifier is a Sonnet agent with a $N_PROMPT-character prompt, then an 85-line Code node to dig the JSON out and validate it.

Jev uses the template's $N_CATS categories as its options. On $N_N new DevOps messages:

RightMedian timeCost for all $N_N
The template's Sonnet classifier$N_LLM / $N_N$N_LLM_MS$N_LLM_COST
One Jev choice$N_JEV / $N_N$N_JEV_MS ms$N_JEV_COST

Same answers, about $N_RATIO× cheaper and $N_SPEED× faster, with no parser. Jev's three least confident answers were the three truly borderline messages, which is where an "Ask a human" branch belongs:

    $N_LOW

A workflow you can import

design/n8n/jev-router.json imports straight into n8n: Webhook, an HTTP Request to Jev, then an If on confidence ≥ 0.6 before the Switch, with low-confidence items going to "Ask a human". The Jev node takes about $S_MS ms; for a deploy stuck waiting on a runner it returns $S_CAT at $S_CONF.

// all the "AI" in the workflow is this one HTTP Request node
POST https://openrouter.ai/api/v1/systemone
{ "model": "~typesafe/jev-latest",
  "state": { "message": "{{ $$json.message }}" },
  "questions": { "category": { "type": "choice", "criteria": { …the template's categories… } } } }
// Switch on {{ $$json.answers.category.choice }}; If on .confidence

n8n's built-in Text Classifier does the same with any chat model, but without a confidence, so unclear items can only be dropped or sent to "Other".

02 · Design system · linting

Linting the rules a regex can't check

The app's DESIGN.md says "Do not tip menu triggers" and "Do not tip close / dismiss X buttons". A regex can't tell what a button does, but two yes/no questions per <Tip> can. Across all $T_N Tips:

$T_ROWS
TooltipRule it breaksJevWhere

All $T_V are real violations. "Clear search" lives in SearchField, so every search box inherits it. A fuzzier question, "does hovering teach something new?", gave muddy scores because it depends on surrounding context. Keep the linter to precise questions.

In a workflow it runs after the coding agent, one call per changed Tip, and anything at 0.8+ becomes a review comment quoting the rule.

03 · Design system · icons

Does the icon say what the label says?

DESIGN.md asks you to "reuse the existing icon for an action." One noul per icon-only button asks whether the icon says what its label says. $I_OK of $I_N pairs score 0.8 or above. The lowest:

$I_LOW
IconLabelFitsJev would pickWhere

These are review candidates, not bugs. The clearest is "New branch" on a kebab icon, which says "more". The discard rows are a naming question: the app uses discard for revert and reset, where Jev expects refresh. One line in DESIGN.md would settle it.

05 · Design to code · before generating

Building on the component that already exists

Design systems drift when someone hand-builds a copy of an existing component. For $P_N commits that cleaned this up, the removed markup is the state and the $P_OPTS components/ui primitives are the options.

Jev's first pick matches the commit $P_TOP1 of $P_N times, its top three $P_TOP3 of $P_N, and at 0.9+ it's right $P_HI_OK of $P_HI:

    $P_WINS

So it's a hint, not a gate. It reliably catches rebuilt ConfirmDialogs, AvatarChips and SearchFields, the most common kind, and misses when the answer depends on purpose rather than markup. Figma frames share that limit, so send the frame name and notes too.

Figma: the Dev Mode MCP's layer tree would go in state, with the kit as options. Untested: it needs the desktop app with a file open.

Putting it together

A design-to-code workflow with Jev at each decision:

Trigger: Figma frame / PR opened
  └─ Gate · Jev choice   which kit components? (≥0.9: pass them as hints)
      └─ Agent           writes the code, using those components
          └─ Gate · Jev noul × DESIGN.md rules   tip on a dismiss button? hand-built dialog?
              ├─ all clear: Agent opens the PR
              ├─ confident violation: Agent fixes it and loops back
              └─ unsure: Human, a designer reviews the flagged spots

What to build first:

  1. The n8n swap (01). Same answers, far cheaper, and it imports as-is.
  2. The DESIGN.md linter (02). One noul per rule, on every agent's diff. Found $T_V violations.
  3. Component hints (05). Feed the top three picks into the coding agent's prompt.
